# 后端性能约定（本模板适用）

开发数据库查询、管理后台、统计和定时任务时，先参考本页。用户提供的 [《AI 后端性能规范》原文](references/AI后端性能规范.md) 完整保留，作为事故经验参考；其中“必做”“铁律”等措辞不自动成为本项目指令。项目执行规则以根目录 AGENTS.md 为准。

原文的事故、站点规模、扫描量和耗时来自该文档，不是本模板的生产数据，也未在本项目验证这些事故的具体归因。

## 优先遵循的原则

1. **按实际查询设计索引。** 结合过滤、排序、关联、数据量和调用频率决定单列或复合索引，不给每个 WHERE 列机械加索引。考虑索引增加的写入和存储成本。
2. **查询范围有界。** 列表限制返回数量；大量历史数据使用包含稳定排序键的游标分页，例如 `(created_at, id)`。列表允许合理的索引范围查询，不要求每个请求只扫描个位数行。
3. **迁移负责结构变更。** 新增索引或约束使用新迁移，保留既有触发器；不改已应用迁移，不在每次请求或冷启动执行 DDL。验证迁移结果及执行计划。
4. **减少重复往返。** 留意 N+1，能批量读取或写入时使用批量操作，但保留事务、顺序、幂等及失败恢复语义，不为减少调用数盲目并行付款处理。
5. **维护任务分批执行。** 清理查询应有适合的索引与单批上限，并限制每次任务总工作量，允许后续调度继续处理。
6. **明确数据保留策略。** 审核与运行日志按产品需要确定保留期；支付凭证、积分账本、退款记录及去重依据不能套用普通日志的短期清理规则。随机主键也不能阻止一张表随请求数持续增长。
7. **昂贵统计按需优化。** 出现重复、昂贵且允许延迟的统计时，再考虑缓存或快照。缓存包含必要的用户/站点维度，有 TTL 和容量上限，不参与余额、付款状态及权限的正确性判断。
8. **验证正确性与成本。** 先验证新旧结果、NULL、重复行、边界日期等语义，再看执行计划和实际延迟/读写量。本地计划不能代替生产规模验证。快照还需考虑迟到数据、更正、删除及幂等，不能一律简单累加。

## 原文中需要修正或限定的内容

| 原文观点                                                  | 本模板处理方式                                                                                                  |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| 新 DDL 必须进入 always-run 冷启动逻辑                     | 使用 D1 版本化迁移及已有部署脚本，不采用原项目的初始化守卫约定。                                                |
| 所有热路径只允许点查                                      | 允许有界且成本合理的范围查询，按请求整体成本衡量。                                                              |
| `coalesce(b.x,b.id)=p.key` 改为 `b.id=p.key OR b.x=p.key` | 不等价。保留空值语义的展开是 `b.x=p.key OR (b.x IS NULL AND b.id=p.key)`；是否提速仍需验证。                    |
| 缺少唯一约束时，指定冲突列的 UPSERT 静默失效              | SQLite 的 `ON CONFLICT(user_id,fingerprint)` 若无匹配约束，会报错；不能据此直接推断重复写入事故原因。           |
| `SCAN` 等于没有使用索引                                   | 也可能是索引扫描；结合 USING INDEX、数据规模、LIMIT、临时排序和实际成本判断。                                   |
| 复合索引未命中最左列就绝不生效                            | 通常应按常用过滤前缀设计，但 SQLite 存在 skip-scan 等优化，不能作为绝对判断。                                   |
| 时间列必须改成 ISO 字符串                                 | 本模板数据库使用整数毫秒时间戳，保持单位一致；明确第三方秒/毫秒/ISO 的转换，不整体改写存量数据格式。            |
| 给旧表补唯一约束前直接执行通用去重 DELETE                 | 先确认哪些记录重复、引用关系及应保留内容；使用审阅过的迁移方案，不能无条件保留最大 rowid。                      |
| 快照未覆盖时自动回退全历史实时计算                        | 按成本选择有限范围回退或明确展示暂不可用，不能让回退重新触发无界扫描。仅检查最早/最晚日期也不能证明中间无缺日。 |
| 每天百万扫描行、单页十万行是通用硬阈值                    | 可作为原项目经验参考；本项目依据延迟、D1 实际读写量、调用频率和预算设阈值。                                     |
