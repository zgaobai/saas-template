# AI 后端性能规范（开发前必读）

---

## 一、写 SQL 前的思考顺序（必做）

1. **先估扫描量**：这条查询会扫多少行？它在什么路径上（用户热路径 / 高频 cron / 低频后台）？
2. **三层优化顺序**：索引点查 > 索引范围扫描 > 全表聚合。
3. **路径决定标准**：
   - 用户热路径（每个请求都执行）：只允许索引点查，扫行数应为个位数；
   - 高频定时任务（每分钟 / 每 5 分钟）：必须走索引范围扫描；
   - 低频管理后台：可容忍范围扫描，但**禁止**对大表做无界 group by / 全表聚合（走快照，见第三章）。⚠️ 管理后台不是低频豁免区，管理员排障操作强度等效用户热路径，标准向热路径看齐——冲突处以第六章为准；
   - 任何路径：禁止无分页的大结果集查询；深分页禁止大 `OFFSET`（O(offset) 扫描），改用 keyset 方式：`where id > 上页末id order by id limit ?`。

## 二、什么情况下需要索引（判定清单）

满足任一条即必须建索引，并在上线时验证索引真实存在：

| 场景 | 要求 |
|------|------|
| 每个请求都执行的查询（鉴权 token 查 session、配置读取） | 无条件建索引，哪怕表很小 |
| WHERE 等值 / 范围条件列 | 建单列或复合索引 |
| JOIN / 子查询的关联列 | 双方都要有索引 |
| ORDER BY + LIMIT 的排序列 | 排序列建索引，避免全表排序 |
| 高频 cron 的过滤条件 | 用复合索引覆盖组合条件，如 `(status, created_at)` |
| `count(distinct ...)`、`group by` 的列 | 仅当查询高频时建；低频改走快照 |

**判定公式**：`查询频率 × 每次扫描行数` 达到「每天百万行」量级即必须治理。

**复合索引列顺序**：等值条件列在前、范围条件列在后（如 `(status, created_at)`），并遵循最左前缀原则——查询条件必须从最左列开始命中，否则复合索引不生效。

### 建索引的三条铁律（违反 = 索引根本不存在）

1. **DDL 位置**：初始化建表链（如 `applySchema`）在已有库上会被版本守卫 / ready 标记短路，**新 DDL 写在这里永远不执行**。必须放在「每次冷启动必跑」的 always-run 块中。
2. **版本递增**：有 schema 版本守卫的项目，新增/修改 DDL 必须递增版本号（如 `SCHEMA_VERSION`），否则 always-run 块同样被短路。⚠️ 以源码当前值为准递增，不要相信记忆中的旧值。
3. **顺序约束**：索引必须放在对应 `CREATE TABLE` 之后（全新空库按顺序执行，索引先于建表会直接报 no such table）。

**上线后必须验证**（部署 ≠ 生效）：

```bash
# 确认表/索引真实存在
wrangler d1 execute <db> --remote --json --command \
  "select count(*) from sqlite_master where name='<对象名>'"
# 首个请求触发建库后验证；跨 session 读有秒级延迟，查不到先重触发请求再查
```

### 索引失效的典型写法（禁止）

| 禁止写法 | 后果 | 正确改法 |
|----------|------|----------|
| `where a.col = '常量' \|\| b.col`（表达式关联 join） | 优化器无法反解，b 表退化为嵌套全表扫描（实测 3800 万行/次） | 把常量前缀留给 `like` + `substr()` 反解：`a.col like '常量%' and substr(a.col, N) = b.col` |
| `join b on coalesce(b.x, b.id) = p.key`（函数包裹 join 键） | 索引失效，p 每行触发 b 表全扫（实测 5.9 万行/次放大） | 改写为可索引的等价 OR：`b.id = p.key or b.x = p.key`，EXPLAIN 应显示 `MULTI-INDEX OR` 双索引查找 |
| 列上套函数：`where date(col) >= x` / `strftime(...) 包裹列` / `where coalesce(x, y) = 常量` | 函数/表达式包裹列不可走索引 | 函数只放常量侧：`col >= strftime('%Y-%m-%dT%H:%M:%fZ','now','-30 minutes')`；coalesce 条件展开为 `x = c or (x is null and y = c)` |
| `like '%xxx'` 前缀通配 | 全表扫描 | 前缀匹配 `like 'xxx%'` 可走索引（用户输入中的 `%`/`_` 必须转义并声明 `escape '\'`）；中缀搜索需求交给专门索引或降频 |
| SQL 模板字符串里写 `// 注释` | SQLite 只认 `--` 注释，`//` 被当除号 → 语法错误 → 接口 500 | SQL 模板内只允许 `--` 或干脆不写注释，解释放代码注释层 |

### 改写后如何验证等价与提速

- **语义等价**：用 `EXCEPT` 双向差分对比新旧写法结果集，diff=0 才可替换（注意线上数据在持续变化，比总量不如比 mismatch）；
- **性能**：实际计时对比（案例：改写后 69ms / 扫 14 万行 vs 原来 6782ms / 扫 3798 万行）；
- **执行计划**：`explain query plan` 有 `SCAN` 字样即全表扫描（注意方言差异可能导致 explain 本身报错，报错就退回实测计时；OR 形式的正确形态是 `MULTI-INDEX OR` + 分支各自 `USING INDEX`）。

### 代码层查询模式：禁止 N+1

循环体内逐条查询（读 N+1）或逐条 INSERT（写 N+1）会把一次请求放大为 N 次数据库往返，SQL 本身再优也救不回来：

- 读：把循环内的单条查询合并为 `in (...)` 批量查询，一次取回后内存关联；
- 写：批量写入用 batch 接口（如 D1 `db.batch()`）或多值 `insert into ... values (...), (...)`，禁止循环内单条提交。

## 三、什么情况下统计走定时快照（判定清单）

**满足以下特征即应做快照，而不是每次请求实时算**：

1. 全表 / 大范围 `group by`、累计型指标（历史 TopN、历史单日峰值、总量排行）；
2. 数据时效容忍到天 / 小时级；
3. 查询读多写少，且每次请求都要重算同样的东西。

**反例（我们付出的代价）**：后台排行榜 4 个累计 Top10 + 报表 6 个历史峰值，每次打开页面都对数百万行大表全表 group by × 10 次。

### 标准模式：每日快照 + 增量合并

- **快照表设计**：`(site, stat_date)` 复合主键（每站点/产品一天一行；单站点单产品可退化为 `stat_date` 单列主键）+ 指标 JSON 列 + **`as_of` 时间戳**（标记快照数据截至时刻，增量合并的锚点），生成时 `upsert on conflict do update`；
- **生成**：每日低峰 cron 自动计算「昨天」的快照；首次上线用 backfill 补历史，**每次最多补 N 天**（分批，避免单次执行超时）；
- **读取（增量合并）**：读最新快照 → 只对 `时间列 >= as_of` 的增量做实时聚合 → 与快照按 key 累加合并重排。这样快照永远滞后但页面数据实时；
- **渐进启用（重要）**：读取侧必须判断快照是否覆盖完整历史（`min(stat_date) <= 数据起点 && max(stat_date) >= 昨天`），**未覆盖时自动回退旧的实时查询**——保证上线当天行为不变，补齐后自动切换，无需人为干预。回退路径必须打日志/计数器，否则补数失败会造成无人察觉的「永久静默降级」；
- **口径固化**：快照生成时确定统计口径（哪些表、哪些状态算「付费」），多站点/多产品口径可能不同，各自固化写死，不要运行时猜测；
- **时区与日切边界**：`stat_date` 按哪个时区切天（如 UTC+8 自然日）、每日快照 cron 跑在几点，必须写死在代码里，禁止依赖运行环境默认时区；
- **健壮性**：读取快照的代码要防「表不存在」「快照行为空」「快照 JSON 列 parse 失败」三种情况，否则一条 `select` 就让整个接口 500。

### 什么不适合快照

今日实时数据、用户个人明细、支付状态等强实时数据——这些走索引范围扫描（`created_at >= 今天`），天然只扫少量行，不需要快照。

## 四、什么情况下做缓存（判定清单）

**满足「同参数请求重复率高 + 计算昂贵 + 时效容忍分钟级」三项再做缓存**：

| 适用 | 不适用 |
|------|--------|
| 管理后台统计页（管理员反复刷新同一日期范围） | 用户个人数据（缓存会串号，除非按用户隔离） |
| 外部 API 的派生查询（转发成本高） | 金额、余额、支付状态等强一致数据 |
| 几乎不变的全局配置（可放宽到 10 分钟） | 写后立读的场景 |

**实现要点**：

- Map 缓存：key = 查询参数完整序列化，TTL 按容忍度定（统计页 5 分钟足够）；
- 多站点/多产品场景下，缓存 key 必须包含 site/product 维度，否则会跨站串数据；
- **必须有容量上限**（如超过 50 条整体清空），否则内存无界增长；
- Serverless 冷实例环境下缓存生命周期 = 实例生命周期，命中是赚、未命中是常态，不要依赖它做正确性；
- 缓存的是「读结果」不是「写意图」，任何写路径不得经过缓存层。

## 五、上线验证与监控兜底

1. **部署流程**：前端改动必须先 build 再 deploy（deploy 不会自动构建）；部署后用线上产物关键字符串 / 版本号确认真的生效；
2. **DDL 三验证**：版本号递增了 → sqlite_master 里对象存在了 → 实际查询走索引了；
3. **用量告警兜底**：性能问题往往静默烧钱数天（我们的案例烧了 2 天才定位）。配置按小时的数据库读行数 + 写入行数告警（无界插入型表烧的是写入行数，见 6.4），加按小时/按库聚合的用量报表，能从曲线突增直接定位到「哪个时间点开始、哪个查询引入」；
4. **告警本身要治理**：同源告警去重（多站点共享账号级聚合时只让一个点上报）、单位人性化（亿 / 万，不要裸数字）；
5. **教训优先**：每个事故的修复方案要沉淀为规范条款，同类需求出现时先套条款再写代码。

## 六、管理后台、upsert 与数据治理（2026-10 用量告警事故新增）

### 1. 管理后台不是"低频豁免区"

**事故**：`/api/admin/users` 一次页面加载 = count + 列表两条查询，每条都无条件对指纹表（113 万行）做窗口聚合物化（单次共 ~920 万行、P50 4 秒）。管理员排查一次问题，半小时内搜索/翻页/筛选几十次 = 2.3 亿行读取，直接触发小时级用量告警。而该站用户全部业务流量加起来只有告警基线的零头——**元凶是后台，不是用户**。

**条款**：
- 后台页面的 SQL 按「单次加载总扫描行数」审计：`一次页面加载 = 所有接口 × 每接口全部查询`，单次加载超过 10 万行即须治理；
- **展示性数据绝不放进主查询物化**：像"指纹列"这种展示用数据，禁止 join 全表 CTE 来取。正确做法：主查询只取当前页，然后按当前页主键（`user_id in (... 当前页)`）二次点查补充数据（延迟关联 / deferred join 模式）——pageSize≤100 时每次只有几百行；
- count 与列表分开写时，count 只允许必要的过滤条件，展示类 join 一律不进 count；
- count 降频：同条件 count 结果缓存 1–5 分钟，或仅首屏加载时计算、翻页复用，禁止每翻一页都重算 count；
- 管理员排障时的操作强度（每分钟几十次搜索/翻页/筛选）等效于用户热路径，后台查询标准向热路径看齐。

### 2. `on conflict` 依赖的约束必须真实存在

**事故**：代码写了 `insert ... on conflict (user_id, fingerprint) do nothing`，但线上老表没有这个唯一约束（建表 DDL 里的 `primary key` 因表早已存在、`create table if not exists` 跳过而从未生效）→ upsert 语义完全失效，每个登录请求插一行，4 个月膨胀到 113 万行。

**条款**：
- 写 `on conflict` 前，先查 `sqlite_master` 确认 conflict target 的唯一约束/唯一索引真实存在；代码审查把这条当必修项；
- `create table if not exists` 对已存在的老表**什么都不补**——给老库补约束只能靠显式 `create unique index if not exists`（放 always-run 块 + 递增版本号）；
- 建唯一索引前必须先去重，否则 DDL 直接失败。去重标准写法：`delete from t where rowid not in (select max(rowid) from t group by 唯一键列)`。

### 3. INSERT 显式写时间戳，不依赖列 default

**事故**：`created_at TEXT default now()` 写在建表 DDL 里，但老表没有该 default；INSERT 不显式传 created_at → 新插入的行该列全为 NULL。叠加时间格式混存（ISO 与 `new Date().toString()` 两种格式同列），`max(created_at)` 按字符串比较返回假结果（"W" > "2"），差点被误诊为"数据断流 4 个月"——实际功能一直正常，只是时间维度全丢。

**条款**：
- 任何 INSERT 显式写时间列（代码里 `new Date().toISOString()`），**不依赖 DDL default**——老库永远拿不到新 default；
- 时间列统一 ISO 格式写入，禁止混入 `Date.toString()` 格式；对时间列做 min/max 前先检查格式是否唯一（`group by substr(created_at,1,2)`）；
- 诊断"断流/停滞"类问题，先怀疑时间列本身的完整性（NULL、格式混存、字符串排序），再怀疑业务。

### 4. 无界增长的"每请求插入型"表必须收口

**判定**：一张表若在每请求/每登录路径上 INSERT，且没有任何唯一约束、TTL 或清理机制，行数 = 请求数 × 时间，必然失控。

**条款**：这类表上线时就必须有 (a) 唯一键约束（幂等去重）或 (b) 每日快照 cron 顺带清理（只留最近 N 条/30 天）。二者至少其一，上线清单检查项。清理查询自身必须走索引（where 条件列建索引）且分批执行（`delete ... where ... limit N` 循环），避免清理任务自己变成全表扫描。

### 5. 告警去重键用"被测桶"，不用墙上时钟

**事故**：用量告警的去重键取自发送时刻的当前小时，而统计窗口是"上一完整小时"——整点跨越后（07:00 发的仍是 06:00 桶的数据），同一异常被当成新告警重复播报。

**条款**：去重键 = 告警内容里实际统计的时间桶（如 `alert_hour`），不是 `Date.now()` 换算的当前小时。凡是"延迟读旧窗口"的告警都要对齐这两个概念。

### 6. 定位用量异常的最短路径：按查询统计，而不是猜

本次从"收到告警"到"锁定元凶 SQL"只用了两步：D1 后台 → Metrics → **按查询** 视图（按运行时间排序），前两名就是元凶（执行次数、读取行数、P50、时间占比一目了然），再用 `EXPLAIN QUERY PLAN` + `EXCEPT` 差分完成修复验证。收到"读行数暴涨"类告警，第一步永远是打开按查询视图，不要先入为主去查业务流量。
